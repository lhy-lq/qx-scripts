# 04 · 常见报错与排查方法

> 本文所有「官方」结论都能在 `_ref/` 里复核到原文；标 `[待核实]` 的是官方文档没说、只能靠实测确认的。
> 排查顺序建议从 §1 的「五层定位法」走一遍，90% 的问题在 Layer 1–2 就能定位。

---

## 1. 五层定位法：先确定脚本「死在哪一层」

QX 脚本不执行，只有五种可能。**按顺序排除，不要跳层。**

```
Layer 1  MitM 层     —— HTTPS 请求有没有被 QX 解出来？
Layer 2  匹配层      —— rewrite 规则的正则有没有命中的 URL？
Layer 3  加载层      —— QX 有没有找到并读入这个 .js 文件？
Layer 4  执行层      —— 脚本跑起来了没有？跑到了哪一行？
Layer 5  回写层      —— $done 的内容有没有被 QX 用上？
```

### 每层的判定探针

**Layer 1 判定**：在 `[rewrite_local]` 里临时加一条最粗暴的规则，看请求是否被劫持：

```ini
^https?://你的域名/ url reject
```

- 命中后 App 报错 / 白屏 → **MitM 通了**，问题在 Layer 2 之后。
- 毫无变化 → **卡在 Layer 1**，先修 MitM。

MitM 层最常见的三个错（`[官方]` sample.conf:395-400）：

| 症状 | 原因 | 处理 |
|---|---|---|
| HTTP 站点的规则生效，HTTPS 的不生效 | `[mitm] hostname` 里没这个域名 | 加 `hostname = 你的域名` |
| 加了域名还是不生效 | 证书没装或没信任 | 装 CA → 设置 → 通用 → 关于本机 → 证书信任设置 → 打开 |
| 只有部分域名不生效 | **QX 的 MitM 只匹配 TLS SNI 或目标 IP**，不看 HTTP Host 头 | 确认客户端没有开 ECH / 没走 IP 直连 |
| 某个 App 完全不生效 | App 做了证书固定（pinning） | 见 §6.4 |

> 原文（sample.conf）：`Only the TLS SNI or destination address in "hostname" will be handled by MitM.`
> 这句话决定了一件事：**你写在 hostname 里的必须是「握手时发出的那个域名」**。App 如果先连 IP 再发 Host 头，MitM 匹配不到。

**Layer 2 判定**：把规则改成能看见的形式，确认正则本身：

```ini
^https?://api\.example\.com/v1/profile url reject-dict
```

用 `reject-dict` 是因为它返回 `{}` 而不是 404 —— 更容易在 App 里看出「被改了」。返回 404 可能和真实错误混淆。

正则层高频错误：

| 错法 | 为什么错 | 改法 |
|---|---|---|
| `https://api.example.com/` | `.` 是任意字符，且 `?` `&` 没转义 | `^https://api\.example\.com/v1/profile` |
| 忘了 `^` | 可能匹配到 `https://evil.com/?u=https://api.example.com/` | 一律加 `^` |
| 正则里带 query string 参数 | URL 里 `?a=1&b=2` 每次不同 | **只匹到 path 为止**，参数在脚本里判 |
| 用 `\?` 匹参数却漏了 `&` | `&` 在正则里也是普通字符，本身没问题但易错 | 只匹路径 |
| 拿浏览器抓的 URL 直接粘 | 浏览器会编码，QX 拿到的是**未编码**的原串 | 用 QX 日志里的实际 URL `[待核实]` |
| `^(https?)://` 用了分组 | QX 的匹配是整串 regex test，分组无害但会掩盖笔误 | 用 `https?://` 即可 |

**Layer 3 判定**：QX 找不到文件时通常**静默失败**（不报错、不执行）`[待核实]`。所以要用「不可能沉默」的探针——在脚本第一行放通知：

```js
$notify("QX", "script loaded", "v1");
```

脚本能弹通知 = 文件被读进来了。**注意**：如果这条通知都没弹，但 Layer 1/2 都过了，几乎一定是路径问题。

路径硬约束（`[官方]` sample.conf:298）：

> `The scripts for script-request-header, script-request-body, script-response-header, script-response-body, script-echo-response and script-analyze-echo-response should be saved in local "On My iPhone - Quantumult X - Scripts" or "iCloud Drive - Quantumult X - Scripts".`

即：**rewrite 类脚本只认这两个目录**（或用 https 远程 URL）。`[task_local]` 同一条约束（sample.conf:333 对 task 也写了同样的话）。

| 错法 | 结果 |
|---|---|
| 放在「我的 iPhone → 下载」里 | 找不到 |
| 文件名带中文/空格 | 找不到 `[待核实]` |
| 用了 `脚本名.js` 但实际叫 `脚本名.JS` | 找不到（大小写敏感） |
| 放在 `Quantumult X` 根目录而不是 `Scripts` 子目录 | 找不到 |
| 用 iCloud 但没开 iCloud Drive | 找不到 |
| 远程 URL 用 `http://` | 官方示例清一色 `https://`，http 能否加载 `[待核实]` |

**Layer 4 判定**：脚本加载了但执行报错。QX 的报错**不会弹窗**，只会进日志。所以执行层的排查核心是**日志可见性**，见 §2。

**Layer 5 判定**：脚本执行完了但界面无变化。见 §7「$done 写回失败」。

## 2. 让日志真的能看见（这是排查的前提）

`[官方]` sample.conf:296：

> `The console.log(message) will output logs to Quantumult log file.`

官方**只说了「写日志文件」，没说 UI 在哪看**。所以别赌 UI 入口，用下面三个通道，按可靠性排序：

### 通道 A：`$notify` 弹通知（最可靠，不依赖 UI）

```js
// 调试期专用：把任意值变成一条通知
function dbg(tag, v) {
    var s;
    try { s = (typeof v === "string") ? v : JSON.stringify(v); }
    catch (e) { s = String(v); }
    $notify("QX-DBG", tag, String(s).slice(0, 400));
}
```

iOS 通知正文有长度上限，所以 `.slice(0, 400)`。这是**唯一不依赖任何 App UI 的日志通道**，排查期就该用它。

### 通道 B：`console.log` + QX 日志页

```js
console.log("[checkin] step1 url=" + url);
```

日志入口随 QX 版本变化，`[待核实]` 具体位置。用通道 A 交叉验证：如果 `$notify` 弹了但日志页看不到，就是入口没找对，不是脚本的问题。

### 通道 C：`$prefs` 落盘，事后读

```js
// 写
$prefs.setValueForKey(JSON.stringify(logArr), "dbg_log");
// 另起一个 event-interaction 任务去读并 $notify 出来
```

适合排查**定时任务**（`[task_local]`）——定时任务弹通知会打扰你，落盘更安静。

### 官方示例里的超时自打印（`[官方]` sample-task.js:19-27）

```js
// Script engine timeout, unit: ms.
if (args["force-timeout"] !== undefined) {
    const forceTimeout = args["force-timeout"];
    setTimeout(() => {
        console.log("Force exit for " + forceTimeout + " ms timeout.");
        $done();
    }, parseInt(forceTimeout));
}
```

这就是 QX **官方推荐的超时兜底写法**：用 `setTimeout` 自己掐。注意它调的是裸 `$done()`。

## 3. 报错总表：按错误信息查

> QX 的 JS 引擎报错信息**不完整、不带行号**是常态 `[待核实]`。所以下表按「你看到的现象」组织，不按错误类名。

### 3.1 `xxx is not defined` 系列

| 报错 | 根因 | 修法 |
|---|---|---|
| `$persistentStore is not defined` | **用了 Surge/Loon 的 API** | → `$prefs` |
| `$httpClient is not defined` | 同上 | → `$task.fetch` |
| `$notification is not defined` | 同上 | → `$notify` |
| `$script is not defined` | 同上 | QX **没有** `$script`，删掉相关逻辑 |
| `$argument is not defined` | 同上 | → `$environment.variables` |
| `$utils is not defined` / `$crypto is not defined` | Loon 的 API | QX 无对应，只能自己实现或改方案 |
| `$config is not defined` | Loon 的 API | → `$configuration.sendMessage` |
| `Buffer is not defined` | Node.js API | QX 无 Buffer，用 `Uint8Array` |
| `require is not defined` | Node.js API | QX 无模块系统，把代码复制进来 |
| `process is not defined` | Node.js API | 删掉 |

**这一组占所有「脚本在 Surge 能用、在 QX 不能用」问题的绝大多数。** 官方仓库全文检索 `$script` 为 **0 处** —— 只要看到 `$script`，这个脚本一定不是为 QX 写的。

### 3.2 `Cannot read property 'xxx' of undefined/null`

只有四个高频来源：

| 表达式 | 什么时候 undefined | 修法 |
|---|---|---|
| `$response.body` | ① rewrite 类型是 `script-response-header`（**官方不给 body**）② body 为空 ③ body 是二进制 | 改类型为 `script-response-body`；或改用 `$response.bodyBytes` |
| `$environment.variables` | QX 版本 < v1.5.6 build 918 | `var args = $environment.variables \|\| {};` |
| `JSON.parse(body)` 返回后取字段 | 服务器返回的不是 JSON（HTML 错误页、空串、gzip 未解） | 见 §3.3 |
| `$response.headers['Set-Cookie']` | 该响应确实没这个头 | 判空 |

**统一防护写法**（建议每个脚本开头都放）：

```js
function safeParse(s) {
    if (s === undefined || s === null || s === "") return null;
    try { return JSON.parse(s); } catch (e) {
        console.log("[safeParse] not JSON, head=" + String(s).slice(0, 120));
        return null;
    }
}
var args = (typeof $environment !== "undefined" && $environment.variables) || {};
```

### 3.3 `Unexpected token` / `JSON.parse` 失败

| 原因 | 判别 | 修法 |
|---|---|---|
| 响应是 HTML 错误页（502/登录页） | 打印 `body.slice(0,200)` 看到 `<html` | 先判 `statusCode`，非 200 直接 `$done({})` |
| body 是 gzip 但你没解 | `$response.headers['Content-Encoding'] === 'gzip'` | **QX 在给脚本之前是否已解压，官方未说明** `[待核实]`。稳妥做法：`script-response-body` 拿到的 body 一般是明文，若见乱码则用 `script-response-body` + 检查 `Content-Encoding` |
| body 为空 | `body === ""` | **官方明确：body 为空的 rewrite 不会执行**（sample.conf:290），所以你看到的空多半是 `$done` 传了空 |
| 服务器返回 JSONP（`cb({...})`） | 首字符不是 `{`/`[` | 剥壳：`body.replace(/^[^(]*\(/, "").replace(/\)[;\s]*$/, "")` |
| 返回数组但按对象取值 | `[` 开头 | 按数组处理 |

### 3.4 脚本「不执行」（Layer 1–3 已过，仍无反应）

| 检查项 | 官方依据 | 说明 |
|---|---|---|
| **body 是不是空的** | sample.conf:290 `The body related rewrite will not be executed if the body is empty.` | `script-request-body` / `script-response-body` / `response-body` / `request-body` 全部受此限制。**POST 无 body、GET 请求、204 响应都会静默跳过。** |
| **同一 URL 是不是有两条规则** | issue #124 | 实测**只有一条生效**，后写的覆盖先写的。必须合并成一个脚本，在脚本里用 header/method 分流。 |
| rewrite 类型拼错 | sample.conf 只有这些类型 | 见 §5 类型表。`script-response-bodyy` 不会报错，只是不生效 `[待核实]` |
| 规则被 `;` 注释掉了 | `;`/`#`/`//` 开头是注释 | 官方 sample.conf 里所有示例**都是 `;` 开头的**，直接复制会全部注释掉 —— 这是新手第一大坑 |
| `[rewrite_local]` 写在了别的区块下 | — | 区块头必须单独一行 |
| 用 `url-and-header` 但 header 正则不匹配 | sample.conf:302：**先匹配 URL，URL 不中就不看 header** | 别把关键条件只写在 header 部分 |

⚠️ **新手第一大坑的具体样子**：从官方 sample.conf 复制 `;^http://example\.com/resource6/ url script-response-body response-body.js`，前面的 `;` 是注释，整行失效。**必须手动删掉分号。**

### 3.5 定时任务（`[task_local]`）不跑

| 症状 | 原因 | 修法 |
|---|---|---|
| 到点没反应 | `enabled=true` 没写或写成 `enabled=1` | 写 `, enabled=true` |
| 到点没反应 | cron 段数错 | 官方支持 **5 或 6 段**；先只用 5 段 |
| 到点没反应 | 手机锁屏/低电量，iOS 挂起 | 定时任务依赖 Tunnel 运行；系统可能推迟 `[待核实]` |
| `event-network` 不触发 | **只有 QX Tunnel 在运行时才可能触发**（sample.conf:336） | 确认 VPN 开关是开的 |
| `event-interaction` 不触发 | 同上，且必须有 UIAction 绑定 | 同上 |
| 任务跑了但没输出 | 任务里没有 `$done()` | **每个分支都要 `$done()`**，否则引擎可能挂住 |
| 整行被忽略 | 行内多了不该有的逗号 | `,` 是参数分隔符，脚本 URL 或 tag 里不能有逗号 |

`[task_local]` 行格式（`[官方]` sample.conf:337-344）：

```ini
;cron script [, img-url=..., tag=..., require-devices=ID1, ID2, enabled=true]
* * * * * sample-task.js, tag=Sample, enabled=true
0 8 * * * https://example.com/task.js#key=value&k2=v2, tag=Daily, enabled=true
event-network sample-task3.js
event-interaction sample-task4.js
```

**注意 `require-devices=ID1, ID2` 里的逗号**：官方示例就是 `ID1, ID2` 带空格。这说明解析器对 `key=value` 的分隔是有状态的，**不要自己乱加逗号**。

### 3.6 脚本跑太久

| 现象 | 原因 | 修法 |
|---|---|---|
| App 请求卡住直到超时 | rewrite 脚本里同步等异步结果，但没调 `$done` | 所有异步回调分支必须 `$done()` |
| `$task.fetch` 老是 10 秒失败 | **官方：默认 HTTP 请求超时 10 秒**，不可配置 | 换更快的接口；或拆成两次请求；或改 `[task_local]` 后台跑 |
| 通知里看到超时但不知道卡在哪 | 没有分段日志 | 每步 `console.log`，或按 §2 通道 A 打点 |

**`$task.fetch` 的 10 秒是硬限制**（sample.conf:335：`The default HTTP request timeout is 10 seconds.`），`opts` 里**没有任何 timeout 字段**。这点和 Surge（`timeout` 参数，默认 5s）/ Loon（`with timeout=300`）都不一样。想在 QX 里做 30 秒的请求，唯一路径是 `[task_local]` + 自己 `setTimeout` 兜底 + 接受单次 fetch 仍是 10 秒。

### 3.7 `$done` 相关

| 现象 | 原因 | 修法 |
|---|---|---|
| 请求无限挂起 | 没调 `$done`，或调在未执行的 `if` 分支里 | 用 flag 保证一定调一次 |
| 改 body 没效果 | 用 `$done(body)`（裸字符串），但类型是 `script-response-header` | header 类型只能改 `{status, headers}` |
| 改 header 没效果 | 用 `script-response-body` 只传 headers | `[官方]` sample-rewrite-with-script.js：**`only change the response headers is not allowed for script-response-body`** |
| 改了 `Content-Length` 导致响应截断 | 手改了长度/编码/类型头 | **官方明确：长度与编码相关头 QX 自动处理，不要自己动**（sample.conf:289） |
| 改 `status` 无效（issue #44） | 见 §3.7.1 | 换方案 |

#### 3.7.1 改状态码不生效（issue #44，open）

`[官方]` sample-rewrite-with-script.js 写了：

```js
// Response status can also be optional changed by using $done({body: modifiedBody, headers: modifiedHeaders, status: modifiedStatus}), the modifiedStatus should be like "HTTP/1.1 200 OK"
```

但 issue #44 报告**实际不工作**（字符串、数字 200 都试过）。**未关闭**。

→ **结论**：改状态码**不要依赖 `script-response-body`**。可靠方案是 `script-echo-response`（官方 sample-echo-response.js 明确演示了返回 307 + Location）：

```ini
^https://api\.example\.com/v1/redirect url script-echo-response echo.js
```

```js
$done({
    status: "HTTP/1.1 307 Temporary Redirect",
    headers: {"Location": "https://example.com"},
    body: "Here we go."
});
```

代价：`script-echo-response` 是**伪造整个响应**，拿不到真实响应内容。

### 3.8 `Set-Cookie` 被合并（issue #135，open）

`$response.headers['Set-Cookie']` 会把多个同名头拼成 `"a=1, b=2, c=3"`。原样 `$done({headers})` 回写就破坏 Cookie。

社区 workaround 是给 key 尾部加空格（`headers['Set-Cookie ']`）来骗过合并逻辑 `[待核实，未在官方文档确认]`。

**更稳的思路**：别在 `script-response-header` 里整体回写 headers。只改你需要的那一个字段：

```js
var h = $response.headers;
h['X-My-Flag'] = '1';
// 只回传必要字段，避免整体覆盖触发合并问题
$done({headers: h});
```

仍然会覆盖。**若必须保住多 Set-Cookie，则避开 response-header 脚本，改用 `$task.fetch` 在 `[task_local]` 里自己发请求、自己管理 cookie。** 这是唯一在 QX 里能完全控制多值头的路径。

## 4. 十项开机自检（写任何脚本前贴一遍）

```js
/* ---------- QX 脚本自检模板 ---------- */
// 1. 确认这是 QX，不是 Surge/Loon
if (typeof $prefs === "undefined") {
    // 几乎可以断定：跑在别的工具里，或脚本用了 $persistentStore
    console.log("[FATAL] not a Quantumult X runtime");
}

// 2. 参数兜底
var ARGS = (typeof $environment !== "undefined" && $environment.variables) || {};

// 3. 日志开关（参数 log=1 才打日志，生产环境关掉）
var DEBUG = String(ARGS["log"] || "") === "1";
function log() {
    if (!DEBUG) return;
    var a = Array.prototype.slice.call(arguments).join(" ");
    console.log(a);
}

// 4. 单次 $done 保护
var _done = false;
function done(o) {
    if (_done) { log("[warn] $done called twice, ignored"); return; }
    _done = true;
    $done(o === undefined ? {} : o);
}

// 5. 超时兜底（官方 sample-task.js 同款思路）
function guard(ms) {
    setTimeout(function () {
        log("[warn] guard timeout " + ms + "ms");
        done({});
    }, ms);
}

// 6. JSON 安全解析
function safeParse(s) {
    if (!s) return null;
    try { return JSON.parse(s); } catch (e) { return null; }
}

// 7. header 大小写无关取值
function hget(headers, name) {
    if (!headers) return undefined;
    var lower = name.toLowerCase();
    for (var k in headers) {
        if (k.toLowerCase() === lower) return headers[k];
    }
    return undefined;
}

// 8. 时间戳（QX 有 Date，放心用）
function now() { return Math.floor(Date.now() / 1000); }

// 9. 日期键，用于「今天做过没」
function dayKey() {
    var d = new Date();
    var m = ("0" + (d.getMonth() + 1)).slice(-2);
    var dd = ("0" + d.getDate()).slice(-2);
    return d.getFullYear() + "-" + m + "-" + dd;
}

// 10. 结束
```

**第 7 条特别重要**：QX 的 `$request.headers` key **保留原始大小写**（服务器发 `Content-Type` 就是 `Content-Type`），`headers['content-type']` 会取不到。这是「本地 Node 测通了、QX 里取不到头」的头号原因。

## 5. rewrite 类型速查（选错类型 = 白写）

`[官方]` sample.conf + sample-*.js 归纳：

| 类型 | 拿到什么 | `$done` 能改什么 | 官方出处 |
|---|---|---|---|
| `script-request-header` | `$request.{scheme,method,url,path,headers}` | `{path, headers}` | sample-rewrite-request-header.js |
| `script-request-body` | 上一行 + `$request.body` | `{body, headers, path}` | sample.conf:308 |
| `script-response-header` | `$request.*` + `$response.{statusCode,headers}` | `{status, headers}` | sample-rewrite-response-header.js |
| `script-response-body` | 上一行 + `$response.body` / `.bodyBytes` | `{body, headers, status}`（**不能只改 headers**） | sample-rewrite-with-script.js |
| `script-echo-response` | `$request.*` | `{status, headers, body}` —— **伪造整个响应** | sample-echo-response.js |
| `script-analyze-echo-response` | 同上，但**会等请求 body** | 同上 | sample.conf:300 |

**选择决策树**：

```
要改请求？
├── 只改 header/path          → script-request-header
└── 要改 body                 → script-request-body
要改响应？
├── 只改 header               → script-response-header
├── 要改 body                 → script-response-body
├── 要伪造整个响应（不发给服务器）→ script-echo-response
└── 要伪造且必须看请求 body     → script-analyze-echo-response
```

**注意 `script-echo-response` 的语义**：它是「不转发，直接答」。想「先转发拿到真响应再改」必须用 `script-response-body`。这两者常被混用。

## 6. 十类高频根因（按出现频率排序）

### 6.1 用了 Surge/Loon 的 API（≈40%）

QX 官方仓库 `$script` 出现 **0 次**；`$persistentStore` / `$httpClient` / `$notification` / `$argument` 同样 0 次。见到即改。

### 6.2 `$prefs.setValueForKey` 参数写反（≈15%）

```js
$prefs.setValueForKey(value, key)   // 官方顺序：值在前
$prefs.valueForKey(key)             // 读只有 key
```

写反了**不报错**，只是存到了错误的位置，表现为「明明存了却读不到」。这也是 Surge/Loon 的 `write(data, key)` 顺序，**顺序是一致的**，别记混成 `(key, value)`。

### 6.3 配置行被 `;` 注释（≈10%）

官方 sample.conf 里每一条示例都以 `;` 开头。直接复制 = 全部失效。

### 6.4 证书固定（pinning）（≈8%）

现象：别的 App 都能抓，就这个不行；或只在某些接口上不行。

QX 没有通用的 pinning 绕过能力。可行路径只有：
- 确认该 App 是否有官方提供的调试/测试环境（这才是合规路径）
- 对**自己有源码的 App**，在开发构建里放开 pinning

这条我不提供绕过方案 —— 做了也不稳，且 QX 侧没有对应 API。

### 6.5 body 为空导致静默跳过（≈7%）

官方明文：`The body related rewrite will not be executed if the body is empty.`

**GET 请求也能有 body，但通常没有。** 所以：
- 用 `script-response-body` 匹配一个**返回 204 / 空响应体**的接口 → 脚本永远不跑
- 用 `script-request-body` 匹配 GET → 永远不跑

排法：换成 `script-response-header` 试，如果 header 类能跑 body 类不能跑，就是这个问题。

### 6.6 `$done` 漏调 / 重复调（≈6%）

漏调的后果比重复调严重（请求挂起）。用 §4 的 `done()` 包装。

### 6.7 正则不匹配（≈6%）

见 §1 Layer 2 的表。**最省事的调试法**：先用 `reject` 系列确认规则命中，再把 `reject` 换成脚本。

### 6.8 多脚本同 URL 只生效一条（≈4%，issue #124）

QX 没有多条件匹配。同一 URL 只能挂一个脚本，其余要在脚本内分流：

```js
var bundleId = $request.headers["X-Client-Bundle-ID"];
if (bundleId === "com.a.app") { handleA(); }
else if (bundleId === "com.b.app") { handleB(); }
else { $done({}); }
```

### 6.9 header 大小写（≈3%）

见 §4 第 7 条。

### 6.10 定时任务 cron 段数（≈1%）

官方说「支持 5 或 6 段」，但**没说 6 段每段是什么**。Loon 官方明确 6 段 = `秒 分 时 日 月 周`，QX 大概率一致但**未确认** `[待核实]`。

**实践建议：只用 5 段（分 时 日 月 周）。** 需要秒级精度就在脚本里循环 `setTimeout`，但那会耗电，不值得。

## 7. `$done` 写回失败专项

`$done` 的合法字段（按 rewrite 类型）：

| 类型 | 合法字段 | 非法/无效 |
|---|---|---|
| request-header | `path`, `headers` | `body`, `url` |
| request-body | `body`, `headers`, `path` | `url`（**issue #99：改 `url` 无效**） |
| response-header | `status`, `headers` | `body` |
| response-body | `body`, `bodyBytes`, `headers`, `status` | — |
| echo-response | `status`, `headers`, `body` | — |

**三个必背约束**（`[官方]`）：

1. **不要动 `Content-Length` / `Content-Type` / `Content-Encoding`**
   sample-rewrite-with-script.js：`please do not change the content length, type and encoding field.`
   sample.conf:289：`The length and encoding related HTTP header fields will be automatically processed by Quantumult if the "rewrite" is body related.`

2. **`script-response-body` 不能只改 headers**
   sample-rewrite-with-script.js：`only change the response headers is not allowed for script-response-body.`
   要只改 header，就换成 `script-response-header`。

3. **`$done({})` 是「不改动」**
   sample-rewrite-response-header.js 和 sample-rewrite-request-header.js 都写了 `// $done({}); // Not changed.`
   → **所有「什么都不做」的分支都写 `$done({})`，不要写裸 `$done()`**（裸 `$done()` 在 rewrite 里的语义官方未文档化 `[待核实]`；但在 `[task_local]` 里官方示例用的就是 `$done()`）。

## 8. 二进制专项

| 事实 | 出处 |
|---|---|
| `$response.bodyBytes` 是 **ArrayBuffer** | sample-bytes-rewrite.js |
| 需要 QX v1.0.19-build480 + iOS 14，或 v1.0.21-build535 + iOS 13 | 同上 `@supported` |
| `$iCloud.readFile` 返回 **Uint8Array** | sample-icloud-storage.js |
| **两种类型不能直接混用** | 需要显式切片 |

**官方给的转换写法**（sample-bytes-rewrite.js 注释原文）：

```js
// If you are getting buffer directly from another Uint8Array, you probably want slicing the results.
// The otherUint8 is a Uint8Array from somewhere else.
$done({bodyBytes: otherUint8.buffer.slice(otherUint8.byteOffset, otherUint8.byteLength + otherUint8.byteOffset)});
```

**为什么必须 `slice` 而不是直接 `.buffer`**：
`Uint8Array` 可能只是某个更大 `ArrayBuffer` 的一个视图（`byteOffset ≠ 0`，或 `byteLength < buffer.byteLength`）。直接 `.buffer` 会**带上整个底层缓冲区**，多出来的字节会破坏图片/文件。这是二进制改写的第一大坑。

**从零造 buffer**（官方同文件）：

```js
var buffer = new ArrayBuffer(8);
var uint8 = new Uint8Array(buffer);
uint8[0] = 3;
uint8[7] = 5;
$done({bodyBytes: buffer});
```

**判二进制**：

```js
var ct = hget($response.headers, "Content-Type") || "";
var isBinary = /^(image|audio|video|application\/octet-stream|application\/zip)/.test(ct);
```

## 9. `$task.fetch` 专项

```js
$task.fetch({
    url: "https://example.com/api",
    method: "POST",
    headers: {"Content-Type": "application/json"},
    body: JSON.stringify({a: 1}),
    opts: {
        'redirection': true,        // 默认 true，build 210+
        'skip-cert-verify': false,  // 默认 false，build 649+
        'auto-cookie': false        // 默认 false，build 934+（更早的版本等效 true！）
    }
}).then(function (resp) {
    // resp.statusCode, resp.headers, resp.body, resp.bodyBytes
}, function (reason) {
    // reason.error
});
```

| 坑 | 说明 |
|---|---|
| **只有 `$task.fetch` 一个方法** | 没有 `$task.fetch.get/post`。方法写在 `method` 字段 |
| **`auto-cookie` 默认值随版本翻转** | build 934 之前**忽略该字段、等效 true**；之后默认 false。签到脚本必须显式写 `'auto-cookie': true` |
| **10 秒硬超时** | `opts` 里无 timeout 字段 |
| **`policy` 会失去连接复用** | 官方明说。批量请求别用 |
| **`filter` 已废弃** | v1.0.17 起。>512KB 才值得用，<128KB 不建议；返回 >16KB 会报错；filter 内不能调任何 QX API |
| **串行请求写法** | 官方：`A $task.fetch() can be embeded in the completion handler of another $task.fetch()` —— 在 then 里再发下一个 |
| **没有并发上限说明** | `[待核实]`。实测建议自己限到 3–5 并发 |
| **`body` 必须是字符串** | 传对象会变成 `[object Object]`，要 `JSON.stringify` |

**串行模板**（官方推荐形态）：

```js
function step1() {
    return $task.fetch({url: URL1, headers: H}).then(function (r) { return r.body; });
}
function step2(token) {
    return $task.fetch({url: URL2, method: "POST", headers: H, body: "t=" + token})
        .then(function (r) { return r.body; });
}

step1().then(step2).then(function (finalBody) {
    log(finalBody);
    done({});
}, function (e) {
    log("[ERR] " + (e && e.error));
    done({});
});
```

**Promise 链里抛异常会静默吞掉**——`then` 的第二个参数（或末尾 `.catch`）必须写。这是「脚本跑了但什么都没有」的常见原因。
